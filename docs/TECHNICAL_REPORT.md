# 基于 AI 的 5G 网络关键性能指标预测与异常检测系统：项目技术报告

**报告日期：**2026-10-23  

## 摘要

本项目面向 5G 网络运维场景，围绕下行物理资源块相关指标（DLPRB）、下行流量体积（DLThpVol）、下行传输时间（DLThpTime）及测量报告数量（MR_number）四个 KPI，构建了一套集数据预处理、下一小时预测、异常候选识别、关联统计和 Web 可视化于一体的离线 AI 分析原型。项目早期开展了 free5GC/UERANSIM 仿真网络连通性测试及控制面、用户面协议抓包分析；机器学习部分采用公开 gotsf-ds 波束级 KPI 时间序列。

公开数据涵盖 2,880 个波束、840 个小时、合计 2,419,200 条波束小时观测。训练与测试按时间先后划分为 672 与 168 小时，模型对 483,840 条测试观测进行评估。使用传统 ML 与 LSTM、GRU、Transformer 进行下一小时预测。保存的历史实验中，GRU 在 DLPRB、DLThpTime、MR_number 上取得最高 R²（分别约 0.808、0.715、0.886）；RandomForest 在 DLThpVol 上取得最高 R²（约 0.615）。异常检测采用 3σ、IQR、Isolation Forest 和 One-Class SVM；对完整测试集使用 `IsolationForest AND (3σ OR IQR)` 产生 3,165 条共识异常候选，占 0.65%。检测输出定义为需要进一步排查的异常候选，采用候选标记率与 KPI 关联统计描述结果。

系统采用 Python、Pandas、scikit-learn、PyTorch、Streamlit 和 WebSocket，集成数据下载与预处理、模型训练及测试评估、实验版本管理、实际 KPI 预测、异常检测和候选 KPI 关联分析六个 Web 模块。训练过程实时显示日志，测试结果与模型权重按实验版本保存。

## 1. 背景、目标和系统边界

5G 网络产生大量动态变化的性能测量数据。基于历史 KPI 的短时预测有助于提前观察性能趋势，异常检测可将海量观测压缩为人工优先排查的候选事件。项目计划要求先搭建 5G 仿真环境并完成协议分析，再建立 KPI 时间序列与预测、异常检测模块，最后使用 Web 平台统一展示并完成技术报告与演示。

## 2. 总体架构与实现

系统的逻辑架构如下。训练阶段产出模型权重和测试报告；推理阶段使用已保存权重处理用户输入：

```text

公开 gotsf-ds 数据 → 下载、审计、预处理 → 特征构建
                                          │
                    ┌─────────────────────┴───────────────────┐
                    ▼                                         ▼
           传统 ML / 深度学习训练                         异常检测训练
                    │                                         │
                    └─────────────────────┬───────────────────┘
                                          ▼
                  实验归档：权重、参数、测试指标与图表
                                          │
                   ┌──────────────────────┴──────────────────┐
                   ▼                                         ▼
            训练后测试集评估                            实际权重 + 输入 CSV

具体职责分别位于 `src/core/`（通用配置）、`src/data/`（数据处理）、`src/models/`（算法、训练、推理）、`src/analysis/`（统计分析）、`src/services/`（训练任务与模型版本）、`src/ui/`（Web 页面）。`app.py` 是应用启动入口。神经网络定义统一保存在 `src/models/architectures.py`，可供训练与推理复用。更多结构细节见 `docs/ARCHITECTURE.md`。

## 3. 数据集与数据预处理

实验选择公开 gotsf-ds 波束级 KPI 数据集。四项分析字段为：`DLPRB`、`DLThpVol`、`DLThpTime`、`MR_number`。项目按波束、基站、小区以及小时序号组织面板数据：

| 项目 | 历史实验记录 |
|---|---:|
| 波束数 | 2,880 |
| 小时数 | 840 |
| 总波束小时记录 | 2,419,200 |
| 训练区间 | Time = 0–671，672 小时 |
| 测试区间 | Time = 672–839，168 小时 |
| 训练记录 | 1,935,360 |
| 测试记录 | 483,840 |

数据预处理包含字段检查、时间轴完整性、缺失及异常值检查、按波束对齐、标准化/归一化。项目将 StandardScaler / MinMaxScaler 参数限定在训练区间上估计后应用于测试集，避免测试分布信息进入训练统计量。传统 ML 特征工程构建滞后 1、2、24、168 小时的特征及下一小时预测目标。相关统计文件：`reports/preprocessing_summary.json`、`reports/ml_feature_summary.json`。

数据下载模块从公开 `netop/gotsf-ds` 数据集获取四个固定原始 CSV 文件，保存到 `data/raw/`。审计与预处理分别由 `python -m src.data.audit_kpi_data` 和 `python -m src.data.preprocess_kpi_data` 执行，预处理输出位于 `data/processed/kpi_timeseries.csv`。特征工程脚本 `python -m src.data.build_ml_features` 输出 `data/processed/ml_features.pkl`，作为传统 ML 训练的输入。

`data/` 中的大型文件没有上传 GitHub。

## 4. KPI 预测实验

### 4.1 实验协议和模型

目标是在时间 `t` 已有观测的基础上预测 `t+1` 小时 KPI，训练/测试按时间划分。基线模型为 Persistence（上一观测保持不变）。传统模型包括 LinearRegression、DecisionTree、RandomForest、XGBoost、LightGBM；深度学习包括 LSTM、GRU、Transformer。评估采用 MAE、RMSE、R²，指标在原始 KPI 数值尺度报告。

不同模型的特征和训练机制存在差异，最终比较以保存的同一测试集评估结果为准。

### 4.2 历史预测结果

下表汇总每项 KPI 的历史最佳 R² 模型，以及 Persistence 作为可解释基准的 MAE：

| KPI | 最佳历史 R² 模型 | R² | 对应 MAE | Persistence MAE | MAE 相对改善 |
|---|---|---:|---:|---:|---:|
| DLPRB | GRU | 0.808 | 0.2456 | 0.2982 | 17.64% |
| DLThpVol | RandomForest | 0.615 | 0.2076 | 0.2378 | 12.68% |
| DLThpTime | GRU | 0.715 | 0.2298 | 0.2793 | 17.72% |
| MR_number | GRU | 0.886 | 0.2097 | 0.2459 | 14.71% |

数据源：`reports/week3/w3_ml_dl_all_metrics.csv`、`reports/model_metrics.csv`。

结果表明不同 KPI 的最佳算法并不完全一致：GRU 对三个目标取得较好的拟合，DLThpVol 的最佳 R² 来自 RandomForest。原因可能与特征、分布、非平稳性及模型归纳偏置有关。

历史传统 ML 的逐小时预测汇总保存在 `reports/prediction_timeseries.csv`；深度学习有 `reports/w3_lstm_hourly_predictions.csv`、`w3_gru_hourly_predictions.csv`、`w3_transformer_hourly_predictions.csv`，对应预测图在 `figures/`。第 5 周的跨系列比较由 `src/analysis/compare_model_performance.py` 读取保存的模型指标并形成报告。

### 4.4 测试集评估与 Web 预测功能

MAE 反映平均绝对偏差，RMSE 对较大的预测误差更敏感，R² 衡量模型对测试集数值变化的拟合表现。模型训练完成后，Web 从对应的 `resources/experiments/<run_id>/reports/` 读取测试指标和真实值与预测值的逐小时对比曲线。模型管理页面提供历史正式实验的固定比较结果，并可查看各次新训练实验。

「KPI 预测」负责实际推理：用户生成演示 CSV 或上传历史 KPI CSV，选择已保存的模型，对输入数据之后的下一小时生成预测并导出。推理页面显示预测值；测试集误差指标在训练评估和实验记录中展示。六模块新版界面已实现，待本机回归验收。

## 5. KPI 异常检测

### 5.1 方法

- **3σ**：根据训练区间各波束 KPI 的均值与标准差设置阈值。
- **IQR**：根据训练分位数及四分位距设置上下界。
- **Isolation Forest**：使用标准化 KPI 与因果一阶差分构成的特征，识别与训练分布不同的样本。
- **One-Class SVM**：在采样子集上训练和测试，避免全量样本带来的计算成本。
- **共识筛选**：`IF AND (3σ OR IQR)`，要求 IF 与至少一个统计检测方法同时提示异常。

### 5.2 保存的检测结果

| 方法 | 标记波束小时数 | 标记比例 |
|---|---:|---:|
| 3σ | 22,059 | 4.56% |
| IQR | 51,318 | 10.61% |
| Isolation Forest | 9,900 | 2.05% |
| 共识规则 | 3,165 | 0.65% |

表中四种方法均基于 483,840 条测试波束小时记录。One-Class SVM 在 12,000 条抽样测试记录上的候选标记率为 4.60%，其评估范围单独列示。

IQR 的标记比例比 3σ 高，这一现象可能与阈值宽度、训练分布偏斜/厚尾和时序分布漂移有关。更完整的统计检验与分布指标见 `reports/w4_anomaly_diagnostics_report.md`。

### 5.3 KPI 关联分析

项目对历史完整实验产生的 3,165 条共识候选记录开展 KPI 两两相关分析。DLPRB 与 MR_number 的 Pearson 相关系数约为 0.889，DLPRB 与 DLThpTime 约为 0.697。统计分析按基站进行重采样或聚类稳健处理，并使用 Holm 方法校正多重比较。

Web 的「KPI 关联分析」还可读取当前异常检测会话的输出，按基站、小区、波束和时间索引与输入 KPI 记录精确匹配，再对共识候选计算 Pearson 相关矩阵。关联强度用于描述指标共同变化及提供后续排查线索。该数据集适用于无监督异常候选筛选与探索性 KPI 关联分析。

## 6. 第四阶段集成：Web 应用与实验管理

### 6.1 Web 功能设计

系统采用 Streamlit 构建六模块交互界面。用户可在 Web 内依次完成数据准备、模型训练及测试评估、权重管理、预测推理和异常分析。

| 页面 | 用户操作 | 计算与展示结果 |
|---|---|---|
| 数据管理与预处理 | 下载四项 KPI、审计、预处理、特征构建 | 数据状态、处理结果及特征文件 |
| 模型训练 | 选择算法、调整参数、启动训练、查看实时日志 | 模型权重、保存的训练配置、测试集指标及图表 |
| 模型管理与实验记录 | 查看模型版本、选择历史正式结果或指定 `run_id` | 权重信息、模型性能比较、真实值与预测值曲线 |
| KPI 预测 | 生成演示 CSV 或上传用户数据、选择预测模型 | 下一小时 KPI 数值、可视化与 CSV 导出 |
| 异常检测 | 生成或上传连续且对齐的 KPI 数据、选择检测模型 | 各方法候选标记、逐小时异常率、记录与 CSV 导出 |
| KPI 关联分析 | 分析本次检测结果或指定实验保存结果 | 共识异常候选的 KPI 相关矩阵、样本记录及导出 |

模型训练支持传统 ML、LSTM、GRU、Transformer 和异常检测算法。深度学习参数包含 Epoch、Batch Size、学习率、隐藏维度、时间窗口、早停、样本上限、随机种子和 CPU/CUDA；异常检测可调整 Isolation Forest 污染率及 IF/SVM 抽样量。训练任务由后台受控进程执行，WebSocket 将日志实时传送到页面。

### 6.2 模型与实验产物

每次 Web 训练均生成独立实验标识 `run_id`，目录为 `resources/experiments/<run_id>/`，其中保存 `requested_parameters.json`、模型文件、测试指标、曲线和图表。训练成功后，模型权重及必要元数据发布到 `resources/models/<run_id>/`。

模型训练页面直接读取本次实验的评估结果；模型管理页面支持按实验版本复查。此前完整实验的性能比较保持在仓库顶层 `reports/` 和 `figures/`。这种组织方式同时保留固定的正式研究结论和持续新增的实验记录。

### 6.3 实际预测与异常分析

KPI 预测页面根据用户选择的本机 ML/DL 权重处理输入 CSV，输出各波束的下一小时预测值。系统提供演示 CSV 生成入口，采用预处理后的 KPI 时间序列构造符合模型要求的输入。单次推理结果显示目标小时、预测数值、图表并支持 CSV 导出。

异常检测页面复用已训练的 `anomalies.pkl` 权重，输出 3σ、IQR、Isolation Forest、One-Class SVM 及共识标记。页面展示候选数量、标记率和时间变化；随后可将本次检测结果送入 KPI 关联分析，以相同波束小时的原始 KPI 计算 Pearson 相关矩阵。

系统技术结构详见 `docs/ARCHITECTURE.md`，具体操作见 `USER_GUIDE.md`。

## 7. 测试、问题排查与性能

项目包含以合成数据为基础的推理往返测试、模型归档测试、结构测试、训练参数校验测试和 Windows UTF-8 输出测试。系统开发期间发现并修复了两个典型问题：

- 旧深度学习训练将不同标准化配置的结果合并写入同一历史报告时，触发 `train_scale_mean` 冲突。解决方式：Web 每次训练使用独立实验目录，并将对应权重与训练参数一起归档。
- Windows GBK 子进程无法输出 `R²` 特殊字符，抛出 `UnicodeEncodeError`。解决方式：为后台 Python 子进程统一设置 UTF-8 I/O 编码。

仓库中已设置三类可离线检查的测试：模型预测/异常推理的合成数据往返测试、模型权重版本与训练配置测试、代码和历史报告契约测试。建议在项目根目录执行：

```powershell
python -m pip check
python -m compileall -q src app.py
python -m unittest discover -s tests -v
python -m unittest test_inference test_model_registry -v
```

随后运行 `python -m src.data.prepare_demo_inputs`，使用生成的预测与异常检测 CSV 在 Web 中**实际点击**运行、导出。

### 7.2 最终源码结构审查

本轮从完整仓库核对了模块职责、公共参数、训练和推理数据契约、输出目录及测试入口，修订内容主要包括：

- **公共参数清单**：四项 KPI、波束身份、公开数据集四个文件名、历史测试起点 672、传统 ML 滞后窗口及最短推理历史集中到 `src/core/config.py`；各训练、数据处理及推理模块引用统一定义。具体定义、单位、引用位置及归属登记在 `docs/ARCHITECTURE.md`。

- **源码职责**：`src.data` 执行数据处理；`src.models` 负责算法训练与模型推理；`src.analysis` 负责统计计算；`src.services` 管理后台运行、权重发布和日志；`src.ui` 负责交互及数据展示。注释集中解释输入输出、特征尺度、时间划分与模型兼容性。
- **结果保护**：保留既有完整实验的 `reports/`、`figures/`；Web 新训练在 `resources/experiments/<run_id>/` 保存指标、曲线及参数，在 `resources/models/<run_id>/` 发布模型权重。新增配置与模型输出的对应测试，检查多个版本间的结果隔离。
- **测试约束**：补充共享配置、模型专属参数、三种 DL 网络输出形状及异常候选 KPI 记录对齐测试。新增测试还需在目标 Windows 环境执行，并配合 Streamlit 手动验收。此前 26 项通过的记录仅对应原先测试版本。

本轮维护采取局部修改方式，保留历史训练算法、既有正式实验数值和已验证的预测／异常检测接口。源码归档覆盖应用入口、数据及算法模块、服务、页面、测试和文档；大型原始数据、处理中间文件、独立模型权重由本机单独保存。

## 9. 结论

本项目完成了基于公开 5G 波束级 KPI 数据的预测与异常检测研究，并将数据准备、模型训练评估、权重版本管理、实际 KPI 预测、异常检测及关联分析整理为统一的 Streamlit 系统。正式历史实验显示 GRU 和 RandomForest 在不同 KPI 上具有各自优势；多方法共识规则从完整测试集中筛选出 3,165 条异常候选，为人工排查提供了重点样本。六模块 Web 界面已完成代码集成，最终交付以本机回归测试结果为准。
